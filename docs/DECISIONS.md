# 选型记录

只记录做过对照实验、有数据支撑的结论，以及被淘汰方案的淘汰原因。所有数字都来自实测，样本量已标注。

## 为什么不用现成的检测器

目标是「图片进，短语+框出」，不预设类别表。试过的路线：

| 方案 | 为什么不用 |
|---|---|
| YOLOE prompt-free | 输出受内置词表约束（4585 类），CC3M 这种网络图库大量概念不在表内 |
| SAM 3 / mask-generation | 出 mask 不出语义，还得再接一个命名模型；且网格采样出的 mask 与"物体"不对齐 |
| MaskFormer 系 | 闭集语义分割，类别表问题同上 |
| DINO-X / VL-SAM-V2 | 需要提供候选类别或文本 query，不是真正的 open-ended |
| NOVIC | 生成式开放词汇分类，词表空间 42919 远超检测器，但**只分类不出框** —— 无空间定位能力，做不了区域标注 |

结论：**没有单模型能同时做好"发现有什么"和"定位在哪"**。所以拆成 caption 模型 + 定位模型。

## Florence-2 grounding 的行为边界

`<CAPTION_TO_PHRASE_GROUNDING>` 是 seq2seq：输入整段 caption + 图像，模型自己从文本里摘短语并配框。

实测（50 张图 1472 个短语）：**88.5% 的短语能逐字在输入 caption 中找到**。剩下 11.5% 是解码漂移（`a bea`、`black -framed`、`pig tails`），不是模型"看图发明"的新概念。

推论 —— **产出的丰富程度由输入 caption 决定**：

| 驱动文本 | 词数 | 短语/图 | 框/图 |
|---|---|---|---|
| F2 自己的 `<CAPTION>` | 12 | ~3 | ~3 |
| F2 自己的 `<MORE_DETAILED_CAPTION>` | 89 | 7.2 | 9.8 |
| 外部 dense caption | 174 | 23.9 | 39.4 |

所以要提升产出质量，改 caption 的 prompt 或换 caption 模型，**调 Florence-2 没用**。

## caption 模型：gemma4 vs Qwen3.6

同 60 张图、同 prompt、同一判定器校验，2026-08-04 实测：

| 指标 | Qwen3.6-35B-FP8 | gemma-4-26B-A4B |
|---|---|---|
| dense 词数 | 170 | 181 |
| 名词片段密度 | 27.0/图 | **34.3/图** |
| 对 CC3M 原标注的词召回 | 33.7% | **35.2%** |
| **驱动 grounding 后精度下界** | 66.1% | **71.4%** |
| grounding 框数 | **36.5/图** | 29.9/图 |
| 单图耗时 | 0.36 s | 0.60 s |

Qwen 的框更多但精度低 5.3 个点，逐条看是**过度解读**：脑补动作（"whispering or giggling"）、编造细节（球衣号码、材质）。gemma4 更克制、命名更准，还会抓到 Qwen 漏掉的水印文字。

**选 gemma4**：精度是链路的根本，框数可以靠 prompt 补；幻觉一旦进了训练数据就无法挽回。

## grounding 加速：三条路的实测收益

目标是全量吞吐，不是单图延迟。

| 方案 | 实测结果 | 采用 |
|---|---|---|
| beam=3 → 1 | 快 25%（1.23s → 0.98s） | 是 |
| 多开（每卡 2 实例数据并行） | 单卡吞吐 985 → 2100 图/时，8 卡 16k 图/时 | 被 batch 取代 |
| 每卡 4 实例 | 单卡 2600 图/时（+24%），但单图延迟 3.3s → 5.2s（+60%） | 不划算 |
| **batch=8 + 禁 EOS** | **3.85×**（3150ms → 817ms/图），精度无损 | **是** |
| TensorRT | 装通了，但 `torch.compile` 实测 **比基线慢**（1.02s vs 0.93s） | 否 |

**TRT 为什么无效**：F2 只有 0.77B，decode 单步 5.3ms 已接近 H800 算力极限，prefill 只占 2.5%。kernel 融合类优化对这种规模没有空间。且 `trust_remote_code` 自定义架构不在 TRT-LLM 预置列表里，适配成本高、收益 <1.3×。

**batch 精度问题的排查链**（这是本项目最关键的一次调试）：

| 实验 | Jaccard | 结论 |
|---|---|---|
| 单图跑两次 | 1.00 | F2 本身完全确定（`do_sample=False`） |
| batch=2 完整生成 | 0.92 | batch 引入了差异 |
| batch=2 只生成 20 token | **1.00** | 短生成无差异 → 差异不来自 batch 本身 |
| batch=2 禁 EOS 强制 101 token | **前 100 token 完全一致** | **EOS 剔除是唯一差异源** |

根因：generate 在 batch 模式下，某序列先到 EOS 会被剔除，batch 维度 N→N-1 改变了其余序列的 attention 上下文。禁 EOS 让全 batch 同步生成到 `max_new_tokens`，差异消失。

代价：需要在首个 `</s>` 处截断再解析，否则自然结束点之后的重复碎片会污染产出（垃圾短语 32% → 4.6%）。

## 校验方法的可信度

用 gemma4 校验 gemma4 写的短语，存在确认偏误，所以结果只是**精度下界**。

为了量化这个偏误，做过分层抽样人工裁决（`legacy/` 里的 `adjudicate.html`）：从判 YES 的 3229 对和判 NO 的 1104 对各抽 100 个人工复核，按总体权重还原真实精度，同时给 Wilson 95% 区间。设计要点是**必须分层** —— NO 只占总体 25%，随机抽 200 个只有约 51 个 NO，估不准误否率。

这轮人工裁决**未完成**（界面和统计脚本都在 `legacy/`，可复用）。所以当前所有精度数字都应读作下界，可靠的是同判定器下的相对比较。

另外：**CC3M 原 caption 不能当真值**。它是网页 alt-text，含大量视觉不可见信息（人名、事件、地点），所以"与原标注的词重合率最高只有 35%"衡量的是文本相似度，不是标注正确性。
